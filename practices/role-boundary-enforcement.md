# 实践: Role Boundary Enforcement — 任务拆分而非角色越界

> 提炼自 VoiceOS 3.0 神笔角色边界事件

## 问题

多角色协作中，某个角色（如设计师）在执行任务时需要跨出自己职责范围（如需要写 JS 逻辑），如果允许直接越界，会导致：
- 代码质量失控（非专业领域的代码缺乏审查）
- 角色边界模糊，后续任务不知道谁负责什么
- 审核者无法按统一标准审核（不知道该用哪个角色的标准）

## 方案

**当任务需要跨角色边界时，拆分任务而不是放宽规则。**

### 拆分模式

```
原任务: "实现带动画的用户卡片"
  ↓ 拆分为
Part A (角色 A - 前端): 构建骨架 — hooks、state、数据流
Part B (角色 B - 设计): 填充样式 — CSS、动画、视觉细节
```

### 规则

1. **每个角色只改自己域的文件**: 设计师只改 `.css` / `.tsx` 的 className 和 style，不改逻辑
2. **拆分而非越界**: 遇到跨域需求，写进 Spec 拆成多个 Part，分配给不同角色
3. **审核独立检查**: Review 模板增加"角色合规"检查项，确认每个角色没有越界
4. **依赖声明**: 如果 Part B 依赖 Part A 的产出，在 Spec 中明确写出接口（如"Part A 导出 `useCardData` hook"）

### Review 模板中的角色合规检查

```markdown
## 角色合规检查
- [ ] 执行者只修改了其角色域内的文件
- [ ] 没有跨角色的代码（如设计师没有写 JS 逻辑）
- [ ] 如有跨域需求，已在 Spec 中拆分为独立 Part
```

## 为什么有效

- **保持角色专业性**: 每个角色只做自己最擅长的事，代码质量有保障
- **审核标准统一**: 审核者用单一角色的标准审核，不需要混合判断
- **依赖显式化**: 角色间的接口在 Spec 中声明，不是隐式耦合
- **可追溯**: 如果出问题，可以精确定位是哪个角色的 Part 出了错

## 适用条件

- 角色有明确的文件域划分（如设计师改 CSS、前端改 TS、后端改 API）
- 任务中包含跨域需求（UI 改动需要数据层配合）
- 有 Spec 拆分能力（指挥者能在写 Spec 时识别跨域需求并拆分）
- 有审核环节（验证角色是否越界）

## 实战证据

VoiceOS 3.0 B86 中，设计师角色（神笔）跨出边界写了 JS 逻辑，导致后续审核发现类型错误和状态管理问题。协议 v5 引入"拆分模式"后，B109 的 7 个 Part 全部按角色边界拆分执行，**零角色越界违规**。审核者的角色合规检查从"偶尔发现越界"变为"例行确认合规"。
