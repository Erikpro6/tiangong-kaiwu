# 实践: 运维审计节奏

> 来源: VoiceOS 3.0 — 113 batch 中远望独立审计仅 1 次，发现 98 个问题

## 问题

协议定义了"质量三关"（执行者 build → 审核者审逻辑 → 运维跑类型+测试+构建），但实际执行中第三关几乎不存在。结果是审核者通过了的代码，运维一次审计就发现 98 个问题（17 个高优先级）。

根因：运维角色没有明确的触发条件。不像执行者有 Spec 驱动、审核者有 🟢 状态驱动，运维是被动的——等指挥者召唤才出现。

## 方案

### 运维审计触发条件

| 触发条件 | 动作 | 优先级 |
|----------|------|--------|
| 每个 Phase 完成 | 全量标准检查 | 🔴 必须 |
| 每 10 个 batch 完成 | 抽样审计（最近 batch 的技术债） | 🔴 必须 |
| 部署后 1 小时内 | 线上可用性验证 | 🟡 建议 |
| 指挥者主动召唤 | 立即审计 | 按需 |
| 生产故障报告 | 紧急审计（限 P0 问题） | 🔴 必须 |

### 标准检查清单

每次运维审计必须跑完以下全部项目：

```bash
# 1. 类型检查
tsc --noEmit
# 期望: 零错误

# 2. 测试
vitest run
# 期望: 全通过（如有测试文件）

# 3. 构建
{build_command}
# 期望: 零警告

# 4. API 可达性
curl -s {API_BASE}/health
# 期望: 200 + 正确响应

# 5. 安全检查（快速扫描）
# - grep 敏感信息硬编码（API key、token 等）
# - 检查 CORS 配置
# - 检查认证中间件覆盖范围
```

### 审计报告格式

每次审计必须写入文件：`docs/audits/ops-audit-YYYY-MM-DD.md`

```markdown
# 运维审计报告 — YYYY-MM-DD

## 健康状态: 🟢/🟡/🔴

## 标准检查结果
| 检查项 | 结果 | 详情 |
|--------|------|------|
| tsc --noEmit | ✅/❌ | {错误数} |
| vitest run | ✅/❌ | {通过/总数} |
| build | ✅/❌ | {警告数} |
| API 可达性 | ✅/❌ | {响应时间} |
| 安全检查 | ✅/❌ | {发现数} |

## 技术债清单
### 🔴 高优先级
| # | 问题 | 位置 | 建议 |
|---|------|------|------|
| TD-1 | {描述} | {文件}:{行} | {修复方案} |

### 🟡 中优先级
{同上}

### 🟢 低优先级
{同上}

## 建议的下一步
1. {P0 修复项}
2. {P1 修复项}
```

### 运维与审核者的分工

| 维度 | 审核者（Review） | 运维（Ops Audit） |
|------|------------------|-------------------|
| 看什么 | 功能对不对（Spec 符合度） | 代码好不好（类型/测试/构建/安全） |
| 什么时候 | 每个 batch 完成后 | 每 Phase / 每 10 batch / 部署后 |
| 输出 | `docs/reviews/batch-N.md` | `docs/audits/ops-audit-YYYY-MM-DD.md` |
| 能否通过 | ✅ 或 ❌ | 只报告，不通过/不通过（无否决权） |
| 改不改代码 | 不改 | 不改（发现 P0 可紧急修复） |

### 运维审计是部署的前置条件

```
指挥者规划 → 执行者编码 → 审核者审核 → 运维审计 → 指挥者部署
                                              ↑
                                        必须通过这一关
```

运维发现 P0 问题 → 指挥者必须先修复再部署。
运维发现 P1/P2 问题 → 记录但不阻塞部署，排入后续 batch。

### 在 progress.md 中标注运维周期

```markdown
### 运维审计周期
| 审计 | 触发 | 报告 | 状态 |
|------|------|------|------|
| Phase A 完成后 | Phase A 结束 | audits/ops-audit-2026-05-25.md | ✅ |
| B90-B100 完成后 | 10 batch | — | 🔴待执行 |
```

指挥者在规划时同步安排运维周期，运维角色无需被动等待。

## 为什么有效

- **定期 > 被动**：不等出问题才审计，按节奏主动检查
- **分工清晰**：审核者看功能，运维看质量——两个视角互补
- **报告留痕**：技术债不是口头说，而是有文件记录、有优先级、有修复建议
- **部署前兜底**：运维审计是上线前的最后一道关

## 适用条件

- 项目达到一定规模（≥20 batch）时引入
- 有独立角色可以运行运维审计（不和审核者同一会话）
- 有 build + 类型检查 + 测试工具链
