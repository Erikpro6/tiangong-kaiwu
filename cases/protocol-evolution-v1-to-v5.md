# 案例研究: 协议进化 v1 → v5 — 12 条经验的根因分析

> 从 VoiceOS 3.0 的 113 个 Batch、12 条进化记录中提炼。每条进化代表一类被永久消除的问题。

## 核心结论

**结构性地预防问题 > 纪律性地要求。**

好的协议不靠 Agent 自觉遵守规则，而是让违规变得不可能（如 Spec Locks 让文件冲突不可能发生），或者让违规立刻被发现（如 verify_cmd 输出必须可见）。

---

## 根因分类

12 条进化按根因分为四类：

| 根因类型 | 数量 | 特征 |
|----------|------|------|
| 协议矛盾 | 3 | 规则分散在多处、互相冲突、Agent 无所适从 |
| 验证缺失 | 3 | 定义了"要验证"但没有强制"验证输出必须可见" |
| 协作流程设计 | 4 | 缺少结构性预防机制，依赖 Agent 自律 |
| 认知偏差 | 2 | Agent 缺少"用户视角"，做出错误假设 |

---

## A类: 协议矛盾（3 条）

### 进化 #2 → #5: 天工 commit 规则矛盾

**Before**: 进化 #2 规定"天工禁止 git commit"（防止乱提交）。5 个 Batch 后发现 31 个文件改动留在工作区，0 个 commit。

**Root Cause**: #2 说"禁止 commit"，AGENTS.md 说"必须 commit"。两处规则矛盾，天工选择更保守的一方。

**After**: AGENTS.md 作为唯一权威。天工必须增量 commit，格式 `feat: batch-N 描述`。CLAUDE.md 只保留唤醒入口。

**教训**: 规则分散在 3 处（CLAUDE.md + AGENTS.md + memory）= 灾难。**唯一权威来源原则**。

### 进化 #6: 天工轮询的启动前提

**Before**: 天工需要"自动执行"指令才创建 CronCreate 轮询。用户期望打开窗口就干活。协议写的是流程，不是意图。

**After**: 天工先扫描 progress.md 直接执行，没任务才启动轮询。删除了 CronCreate 的刚性步骤。

**教训**: 协议应该匹配用户的意图模型，而不是强迫用户适应协议的流程模型。

### 进化 #12: 紧急情况跳过所有角色

**Before**: 用户说"你先执行吧"，北斗直接动手写代码。没有天工、没有审核、没有部署验证。每步省的时间加倍还回来。

**After**: 角色边界是铁律——即使紧急，也要告知用户"这是例外"。部署清单、Build 规范、角色边界三份 feedback 文件同时创建。

**教训**: 规则的价值在最紧急的时刻体现。用户明确说"你不可以因为我要干什么而放弃一些规则"。

## B类: 验证缺失（3 条）

### 进化 #5: Build 验证形同虚设

**Before**: 天工从不 `next build` 就标 🟢。巡天不检查 build，只看代码。5 个 Batch 带着 build error 交工。

**After**: 天工闭环三步——所有 Part 完成 → build 通过 → commit → 标 🟢。缺一不可。

**教训**: "应该验证"和"不验证就不能标完成"是两个完全不同的规则强度。

### 进化 #7: 流程走完 ≠ 产品可用

**Before**: 55 个 Batch 全部通过审核。用户首次测试发现 12 个 Bug。SWR 数据解包遗漏、SQL 字段遗漏、积分显示全为 0。

**After**: 部署检查清单——用户测试前指挥者必须确认: build 通过 + deploy 完成 + 线上 commit = 本地最新 + 关键 API 返回正确。统一 SWR fetcher 封装。

**教训**: 自动化流程缺少最后一环——用户视角的端到端验证。[部署验证实践](../practices/deployment-verification.md) 即来源于此。

### 进化 #10: verify_cmd 没被实际执行

**Before**: Spec 中写了 verify_cmd，但天工可能没实际运行 bash，巡天也没验证输出。"自验"变成了"自述"。

**After**: 天工必须在 Spec 中贴 verify_cmd 的实际输出。巡天检查: 无输出 → FAIL。输出与预期不符 → FAIL。

**教训**: 定义"要验证"是第一步。强制"验证输出必须可见"是第二步。两步都做才有意义。

## C类: 协作流程设计（4 条）

### 进化 #4: 并行拆分策略

**Before**: Track A/B 零文件冲突——因为指挥者手动检查了文件交叉。

**After**: Spec Locks 机制——每个 Spec 声明改动文件列表。指挥者交叉检查，有交集 = 串行，无交集 = 并行。[Spec 文件锁实践](../practices/spec-locks.md) 提炼自这里。

**教训**: 好的并行不需要 Agent 自觉避免冲突，而是让冲突在规划阶段就暴露。

### 进化 #8: 巡天和远望互补

**Before**: 巡天是唯一的质量关卡。它只审代码逻辑和 Spec 符合度，不跑 tsc/vitest/next build。

**After**: 质量三关——天工 build → 巡天审逻辑 → 远望跑类型+测试+构建 → 指挥者部署。远望捕获了巡天遗漏的 6 个 TS 错误 + 1 个测试失败 + 9 个 viewport 警告。

**教训**: 两个不同视角的审核 > 一个视角的深度审核。[运维审计节奏实践](../practices/ops-audit-cadence.md) 即来源于此。

### 进化 #9: Bug 也适合写 Spec

**Before**: 指挥者在"写 Spec 还是直接改"之间犹豫。小 Bug 觉得不值得写 Spec。

**After**: 所有 Bug 都走 Spec 流程。Bug Spec 精简格式: 根因(1-2 句) + 改动文件 + 修复代码 + 验证标准。追溯价值高于编写成本。

**教训**: Spec 的价值不只是给天工看——它让 Bug 有追溯记录，让审核有标准，让进化有输入。

### 进化 #11: 神笔越界的结构性解决

**Before**: 神笔两次越界写 JS（B86/B88）。不是纪律问题——是视觉+交互耦合任务的结构性矛盾。

**After**: 拆分模式——涉及交互逻辑的视觉任务，指挥者必须拆成: 天工搭骨架（CSS class 钩子 + JS 状态绑定）→ 神笔填样式（只改 globals.css）。B109 之后零违规。

**教训**: 重复出现的越界不是纪律问题，是协议的结构性缺陷。[角色边界执行实践](../practices/role-boundary-enforcement.md) 的核心原则。

## D类: 认知偏差（2 条）

### 进化 #3/6: 一步一规划 vs 以终为始

**Before**: 指挥者习惯一个 Batch 一个 Batch 地规划。用户纠正: "先画全景路线图再执行"。

**After**: 以终为始——收到新阶段 → 先定义终点 → 写全景路线图 → 用户确认 → 批量写全部 Spec → 再启动执行。

**教训**: AI Agent 倾向于"先做再说"，但好的规划需要"先想全局再做局部"。

### 进化 #12: 部署三重失误

**Before**: 6 个前端 commit、4 次 build，从未部署。用户在手机测了半小时全是旧代码。诊断方向跑了三次——先怀疑模型切换、再怀疑网络、最后才发现"根本没部署"。

**After**: 部署检查清单——build → postbuild → deploy → curl 验证 → 告知用户"已上线"。用户报线上问题时，第一反应是"部署了吗？"而不是"改代码"。

**教训**: Agent 缺少"用户视角"——不知道用户实际看到的是什么。协议必须包含"确认用户看到的是最新版本"的显式步骤。

---

## 进化趋势

```
v1 (#1-3):   角色定义 + 基础规则
v2 (#4-5):   发现协议矛盾 → 确立唯一权威
v3 (#6-7):   发现验证缺失 → 强化验证闭环
v4 (#8-10):  Harness 优化 → 结构性预防
v5 (#11-12): 小诸葛升级 + 部署铁律
```

一次通过率变化: **33% → 100%**（5 轮进化后）
